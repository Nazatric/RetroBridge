# Security model and limitations

## Current trust model

- APKs, registry files, package metadata, ZIP entries, ELF headers, and library names are untrusted input.
- Imported data stays below the app's private files directory. A generated UUID is part of each guest root so two imports do not share mutable files.
- Registry fields are validated on both write and read. The registry file is opened without following symbolic links. Corrupt registry data causes a visible startup failure; the original file is not silently replaced with an empty registry.
- Structured diagnostic history is app-private, bounded, and atomically replaced; repeat events coalesce while preserving counts. JSON report export can reveal package names, guest paths, library names, symbols, and execution addresses, so review reports before sharing. The log is not encrypted, and process death or storage failure can prevent a final event from being written.
- The filesystem mapper allows only explicit package-private `/data` and app-specific external data/OBB prefixes. It rejects traversal, NULs, unknown roots, and symlink components.
- Clear Data operates only on that import's internal and app-specific external directories. Remove operates only on its validated UUID root and does not follow symlinks.
- APK import copies bytes, reads package metadata, and catalogs native-library names. It performs a bounded read-only ELF preflight (header plus program-header table, with per-library and archive work caps), records structural failures, and never extracts a `.so`; a passing result does not prove dependencies, relocations, symbols, loadability, or launch support. Import does not call the package installer or load guest code.
- Android/data and OBB ZIP imports spool to app-private temporary files, preflight the central directory before opening entries, enforce compressed/uncompressed byte and entry-count quotas, reject traversal and Unix symlink entries, validate package-qualified roots and OBB filenames, then stage before replacing guest files with rollback backups. ZIP64 is not accepted; central-directory metadata is capped at 64 MiB, archive paths at 1,024 UTF-8 bytes, and individual path components at 255 bytes. Current payload limits are 1 GiB compressed / 2 GiB expanded / 50,000 entries / 512 MiB per data file; OBB bundle 2 GiB compressed / 16 GiB expanded / 256 entries / 8 GiB per OBB; raw OBB import 8 GiB.
- ZIP export walks only guest-owned internal, external, and OBB directories without following symlinks, caps traversal at 50,000 paths and output at 49,999 files plus the manifest, and enforces the 16 GiB file-byte quota while streaming to the selected SAF destination. It snapshots file sizes for the JSON inventory/OBB manifest and fails if a file changes during export; a failure can still leave a partial output at the selected destination, which the caller must discard.
- The guest control service is non-exported and runs in `:guest_runtime`. It accepts primitive Messenger fields, re-hashes the stored APK, extracts only strict ARM32 library paths with 64 MiB per-library/192 MiB total caps, verifies SHA-256 at extraction and immediately before native mapping, and uses an instruction-budgeted interpreter with bounded guest memory and app-private VFS. Active sessions are capped at two. Imported native code now does run in this process, but the service shares the app UID and is not a security boundary; never use this prototype to execute untrusted APKs.

## Not a security boundary for guest execution

A process split alone is not a complete sandbox. The service now maps imported ARM32 shared objects into custom guest memory and interprets them; it does not directly jump to guest machine code, but interpreter/thunk defects, CPU exhaustion, parser bugs, filesystem races, Binder/process interactions, and denial-of-service risks can still affect the app process. There is no OS UID/seccomp/mount namespace separation, guest thread scheduler, Android permission mediation, or audited adversarial boundary. APK hashing proves identity/integrity relative to the registry, not trustworthiness. Do not run untrusted APKs.

A POSIX-backed VFS and ARM32 EABI syscall dispatcher mediate a tested subset of guest file, memory, clock, and process calls in the bounded native session. `GuestBionicThunks` separately provides a narrow libc/libm/pthread subset backed by guest memory and the VFS; it does not start guest threads, implement per-thread errno/TLS, or replace Bionic. `GuestAndroidAssetThunks` serves only bounded caller-registered byte blobs and never resolves an arbitrary guest asset path to a host path; APK ZIP assets and Java `AssetManager` are not connected. `GuestAndroidWindowThunks` exposes host-created RGBA_8888 pixel buffers as separately mapped guest memory (outside the general guest heap), capped at 4 Mi pixels and 4096 pixels per side per surface, and 16 MiB total; it has no host-pointer exposure, Java `Surface`, display compositor, or launch integration. `GuestAndroidInputThunks` accepts only host-injected bounded key/motion records; it does not connect to Android system input, attach queues to loopers, dispatch callbacks, or poll guest file descriptors. `GuestHeadlessGlesEglThunks` performs only bounded RGBA clears/scissors over separately mapped window buffers; it has no GPU/display integration, shader execution, or guest-provided host pointers. `GuestOpenSlThunks` copies PCM only from validated guest ranges into host-owned queues capped at 32 buffers per player, 1 MiB per buffer, and 8 MiB aggregate; it has no audio device, callback execution, or recording. Path translation permits only app-private internal/external/OBB roots and rejects traversal and symlink components; it is not a kernel mount namespace and does not protect against every filesystem race. Many syscalls and Bionic APIs, writable shared mappings, guest thread scheduling, Binder, and arbitrary host APIs remain unsupported, and their APK integration is partial: native libraries can reach only the implemented subset. APK ZIP assets/Java AssetManager, Android callbacks, full EGL/GLES, audible audio, arbitrary syscalls/Bionic/JNI, and general framework access remain unsupported. Do not use the prototype to run APKs from untrusted sources as executable guests.

## Planned hardening before broader or untrusted APK execution

- Fuzz ELF parsing and any ZIP/data archive extraction.
- Fuzz the guest allocator and continue bounds-checking every guest read/write and ABI structure conversion.
- Keep host pointers, JNI references, `size_t`, `long`, `off_t`, and host structure layouts behind typed marshaling APIs.
- Deny unimplemented syscalls and symbols with package/library/symbol diagnostics; never resolve an ARM32 symbol by loading an incompatible ARM64 library.
- Add resource limits, cancellation, crash isolation, and per-app storage quota handling.
- Perform an independent security review before broadening launch support or recommending any imported-code execution.
