# Native interfaces and implementation boundaries

The C++ library is platform-neutral so guest-address, memory, ELF, lifecycle, and execution contracts can be host-tested before the Android runtime is allowed to run imported APK code.

- `guest_address.h` / `guest_memory.h`: overflow-checked guest address/range values and sparse, permission-checked guest memory.
- `elf32_image.h` / `elf32_loader.h`: ELF32/ARM parser, PT_LOAD mapping, DT_NEEDED/DT_SONAME metadata, supported ARM REL relocations, symbol lookup, and lifecycle-array validation.
- `native_execution_session.*` / `retrobridge_jni.cpp`: bounded ARM32 session composition, dependency ordering, resolver wiring, constructor/`JNI_OnLoad`/selected-entrypoint execution, teardown, and Kotlin DTO/JNI ownership. Android JNI is built only for the Android shared library; host CTest directly exercises the platform-neutral session class.
- `translation_engine.h` / `arm32_interpreter.h`: execution contract, bounded A32/T32 interpreter subset, SVC callback, guest-address trampoline registry, and explicit unavailable DBT placeholder.
- `guest_heap.h`, `guest_bionic_thunks.*`, the `guest_android_*_thunks.*` bridges, `guest_headless_gles_egl_thunks.*`, `guest_opensl_thunks.*`, `native/vfs/`, and `native/bionic_bridge/arm32_syscall_dispatcher.*`: bounded 32-bit allocator; partial libc/libm/pthread function/data trampolines; caller-registered blob-backed AAsset thunks; host-created headless RGBA_8888 native-window buffers; synthetic host-injected key/motion events with a nonblocking ALooper subset; EGL window surfaces with software color-clear/scissor GLES; an Android OpenSL ES 1.0.1-compatible shared engine/player model with bounded PCM queue storage, recognized no-op engine options, and host draining; app-private POSIX VFS; and explicitly partial ARM EABI syscalls. There is no Java `Surface`, Android system input integration, APK asset provider, GLES draw/shader pipeline, audible audio sink, or guest callback scheduler. The native session installs the thunks and can execute selected APK-sourced ARM32 libraries, but these remain explicit partial APIs rather than a general Android execution pipeline.
- `guest_jni_bridge.*`: synthetic 32-bit JNI/JavaVM tables, opaque local/global refs, marshaled strings/arrays, explicit exceptions, and checked native-method registration; no ART or general Java execution.
- `guest_lifecycle.h`: bounded DT_INIT/DT_INIT_ARRAY and DT_FINI_ARRAY/DT_FINI calls through a temporary guest return thunk.
- `handle_table.h`: generation-checked guest handle map to opaque 64-bit tokens; not a JNI implementation.
- `runtime_capabilities.h`: capability snapshot keeps instruction execution distinct from complete guest-app compatibility.

The host CMake project is verification-only. It cross-runs ARM32 integer, scalar-VFP, and shared-library lifecycle fixtures with the host interpreter; the demo asserts actual guest instructions, relocations, `JNI_OnLoad`, `sqrtf`, selected entrypoint return, VFS writes, and destructor-on-stop. The Android app/runtime build for `arm64-v8a` and `x86_64`; its non-exported service owns the bounded ARM32 shared-library path over Messenger IPC. An API 35 x86_64 emulator instrumentation test imports the signed demo APK, exercises that real service/JNI path, and checks the VFS/lifecycle results. This does not demonstrate arbitrary APK compatibility, Java/Activity execution, or a security boundary.
